# AI Approach

The system uses AI where interpretation benefits from world knowledge, and
deterministic or measured systems where they are more reliable.

| Stage | Mechanism | Reason |
|---|---|---|
| Intent to search plan | Structured output via `LLM_PROVIDER` (Anthropic, OpenRouter, or a local Ollama model) | Natural-language requests need world and shopping context |
| Query to product matching | Local `all-MiniLM-L6-v2` embeddings | Cheap, offline semantic retrieval |
| Conditions | Open-Meteo | Weather and elevation should be measured when possible |
| Explanations | Deterministic composition | Keeps reasons grounded in retrieval evidence |
| Catalogue enrichment | Same `LLMProvider` protocol, offline scripts (`scripts/enrich.py`, `scripts/enrich_suitability.py`) | One-time attribute enrichment, provider-agnostic so it need not cost API credits |

## One Model Call Per Completed Search

The live request path uses one LLM call for interpretation. It returns a
`StructuredQuery` containing:

- intent summary
- shopping buckets
- catalogue-language search phrases
- permitted taxonomy paths
- filters
- resolved dates and location hints
- assumptions
- clarifying questions when needed

Retrieval never sees the raw user sentence. It sees the structured buckets.
That boundary keeps search testable without an LLM and makes the LLM provider
swappable.

## Clarification

Clarifying questions are generated during interpretation only when the missing
detail would materially change the answer. Answers are structured chip values,
for example:

```text
gender:men
price_max:5000
occasion:daily-wear
```

Merging those answers is a deterministic dictionary update, so the
clarification round trip does not require another model call.

## Retrieval

The catalogue is embedded locally. Each bucket is searched independently, and
category gates restrict candidates to the product types the bucket can use.

Ranking combines:

- semantic similarity
- category eligibility
- price and gender filters
- use-case and occasion boosts
- season and temperature fit
- penalties for weak or mismatched evidence

## Weather and Context

The model is not trusted to invent trip weather. When a request includes a place
and dates, the backend attempts to resolve:

- place
- coordinates
- elevation
- temperature range
- precipitation
- forecast or climatology provenance

For obscure places such as mountain passes, the model may propose coordinates,
but elevation is checked before weather is used. If conditions cannot be
established, the value is marked `unobtainable` and the response says ranking
did not use temperature evidence.

## Explanations

Explanations are composed from retrieval evidence rather than generated by a
second model call. This avoids hallucinated specifications and keeps each reason
traceable to product attributes or resolved request context.

Evidence is prioritized by shopper usefulness:

- measured climate fit
- season fit
- use case
- occasion
- material
- rating and review count
- price or discount

## Provider Fallback

An optional second provider can be configured (`LLM_FALLBACK_PROVIDER` +
`FALLBACK_INTERPRET_MODEL`). `FallbackProvider` tries each in order and returns
the first success, so a rate limit or outage on one provider does not drop the
request straight to keyword matching. Each hop carries its own model id: a model
valid on Anthropic is meaningless on OpenRouter, so sharing one `INTERPRET_MODEL`
across providers would guarantee a mismatch on the fallback path.

Falling through is driven by *failure*, never by elapsed time. Every hop
gets the full `INTERPRET_TIMEOUT_S`, and only an `LLMUnavailable` -- a
rejected key, exhausted credit, a rate limit, a transport error, or the
provider's own timeout expiring -- moves to the next provider. An earlier
version also abandoned a hop after a short deadline; that aborted a healthy
provider mid-call (a real interpretation takes ~11s, the deadline was 8s)
and sent every search to keyword matching. Slow is not the same as broken.
Ordering still matters -- put a fast, reliable model first and the free one
behind it.

## Degraded Mode

If no provider is configured, or every provider in the chain fails, the app uses
keyword interpretation and sets `degraded_mode: true`. If the semantic embedding
model is unavailable, it uses a hashing fallback and adds a note.

The goal is to keep the demo usable while making reduced quality explicit -- a
weaker answer should look weaker to the user and to the evaluator, never be
passed off as a full-quality one.
