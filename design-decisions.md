# Design Decisions

## Search Once Per Bucket

A single global search for a trek request returns mostly jackets because warm
clothing dominates the similarity space. The interpreter splits a request into
shopping needs first: layering, footwear, navigation, gifting, occasion wear and
so on.

Retrieval then runs once per bucket, which keeps the result set diverse and
aligned with the actual shopping task.

## Category Gating Is Hard Filtering

Each bucket declares canonical `Category/Subcategory` paths that may fill it.
Anything outside those paths is excluded regardless of semantic score.

This exists because cosine similarity is relative. A product can be the closest
available item while still being the wrong type. Required product type is
therefore treated as a categorical constraint, not as a soft threshold.

## Attribute Boosts Multiply

The scoring shape is:

```text
score = semantic_score * (1 + boosts) - penalties
```

Boosts can reorder relevant products, but they cannot rescue an irrelevant
product with a weak semantic match. This avoids cases where a merely tagged item
beats a genuinely relevant one.

## Search Phrases Are Scored Separately

A bucket can contain several search phrases. They are separate sub-needs, not
one averaged meaning. For example:

```text
headlamp LED
trekking pole
sunscreen SPF50
```

Averaging those into one embedding produces a vague "generic trekking" vector.
Scoring each phrase separately and merging by best match preserves specific
needs.

## Empty Slots Are Reported

When the catalogue cannot cover a required need, the API returns an
`unfilled_slots` entry instead of substituting the nearest available product.

This is important for trust. A wedding suit request should not be "completed"
with unrelated hiking products just because they are the nearest neighbours.

## Two-Axis Taxonomy

Product type is separated from use case:

```text
type:     Footwear/Boots
use case: trekking
```

This allows one product to satisfy many intents without scattering footwear,
outerwear or accessories across duplicated categories.

## Weather Is Looked Up

Trip conditions are not invented by the LLM. The model may propose location
context, but elevation and weather are resolved through Open-Meteo when
possible. Ranking then reads measured numbers, not prose generated by a model.

## Stateless Backend Conversation

The backend does not store conversation state. The frontend folds follow-ups
into a self-contained query and sends that to the API.

This keeps the backend horizontally scalable and avoids server-held state
silently conflicting with a later user correction.

## Visible Assumptions

When a missing detail is safe to assume, the system proceeds and surfaces the
assumption in the UI. When the missing detail would materially change the
recommendation, the API returns `mode: "clarify"`.

## Suitability Severity Has Three Tiers, Not One

Attribute mismatches are not all the same kind of wrong. A product with no
rain protection when heavy rain is expected is a genuine veto for a
rain-specific need; the same product for a "possible light rain" trip is
still wearable, just worse -- a heavy penalty, not an exclusion; a product
one notch less formal than the occasion calls for is a tiebreaker, not an
objection.

`services/suitability.py` keeps these three severities (hard / strong / soft)
separate rather than collapsing them into one penalty, because a single scale
cannot represent "wrong enough to exclude" and "wrong enough to sink" as
different claims. It deliberately reserves `hard` for one narrow case
(water-resistance) rather than extending it to formality too: a wrong veto
is a worse failure than a wrong penalty, and formality is the more
judgement-prone of the two axes.

## Visual Direction

The UI uses a focused editorial style: single page, sharp edges, warm ground,
one accent color, product imagery, compact result groups and explanations placed
close to products. The first screen is the usable assistant rather than a
marketing landing page.
